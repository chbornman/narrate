1Process and truth-store architecture

One Tauri desktop process owns every durable byte. Big or crash-prone model work lives in supervised child processes (llama-server, pp-asr-server); only tiny, fixed-shape models run in-process through ONNX Runtime. The sidecar JSON files beside your images are the truth; SQLite, PPVEC, and the preview cache are rebuildable indexes derived from them. Image bytes reach the webview through a custom photoproof:// protocol, never as base64 over IPC. This shows what runs and where truth lives.

2The five models at a glance

Three runtimes, three acceleration stories. The LLM (llama.cpp) already picks Metal / CUDA / Vulkan / CPU by detected hardware. The ASR runs on CPU by design - a 0.6B streaming model is real-time on a laptop and keeping it off the GPU removes the worst VRAM contention. VAD is tiny and lives on CPU forever. The two embedders (text and image / CLIP) run on CPU in production today; their GPU execution providers (CoreML on Mac, CUDA on NVIDIA) are in progress / planned, gated on an FP16 single-file export. This shows each model's runtime, accelerator, and what it produces.

3Capture flow (voice)

The one path with real-time constraints. You arm the mic (Space / M), silero VAD stamps the authoritative speech onset, and the write-scope is snapshotted at that onset - so words follow your eyes even if you click to the next image mid-sentence. The ASR streams partials and then a final; the event id is minted at onset but the row lands at finalization, folded and written to the sidecar (truth) and the index (derived). Audio never touches disk. This shows the VAD-onset binding rule that makes voice attribution correct.

4Ingest pipeline

A watched root feeds a queue whose rows are the work: each pass is a row in ingest_passes. Discovery hashes the file (BLAKE3 = identity), extracts EXIF, and builds preview tiers (512 px thumb, 2560 px display). The CLIP image-embedding pass and text-embedding of notes run as background passes that yield to voice and interactive search. The caption pass (VLM) and summary generation are spec'd but not built - their pass names exist with no runner. This shows what produces an image's derived data and in what order.

5Search fusion

A query fans out into up to four signals and fuses them with weighted Reciprocal Rank Fusion (k = 60). S1 is your annotation text as vectors (the primary signal), S2 is keyword FTS5 over your words, S3 is machine summaries (M3, awaiting generation), and S4 is visual CLIP matching (the fallback for un-annotated or explicitly visual asks). The text embedder embeds the query once for S1 and S3; the CLIP text tower embeds it only when S4 activates. Your own words outrank the machine's: machine signals only add ways to find an image, never substitute for your words. The LLM query-parse step is mock-only in the shipped app (its slot is None). This shows how a question reaches a photograph.

6Model concurrency: the priority ladder

WHERE models run is half the story; WHEN is governed by a scheduler enforcing a strict priority ladder: live voice > interactive search > background fuel. Arming the mic pauses all background model work (it resumes about 5 s after disarm). An interactive LLM query parse preempts a background LLM job that would otherwise make it wait more than 250 ms. The LLM is one server with two slots (interactive + background, never more); GPU / embedding passes run at concurrency 1. This shows what pauses or preempts what. The ladder is wired today; the background LLM jobs it would schedule (captions, summaries) are M3.

7Fallback chains (robustness)

Robustness is two layers. Per model: try the best accelerator, fall back to CPU, then let just that feature go dark. Per product: the Tier-0 floor is a complete product with no models at all - typed notes, the grease pencil, ratings, and FTS5 keyword search. Every runtime failure (a model that will not download, an execution provider that will not load, a native crash) lands at Tier 0 quietly: voice off is not the app broken, semantic search off still leaves keyword search. This shows that nothing the models add is load-bearing for the journal.
