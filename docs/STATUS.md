# STATUS — capability ledger

Date: 2026-06-12

This file answers one question per spec obligation: exactly what has and has
not been built. It is the capability-grain companion to the packet-grain
ledger in `docs/BUILD-LOOP.md`.

**Standing rule: every work-packet close updates this file** — in the same
commit that updates the BUILD-LOOP ledger row. A row may only move to a
stronger state with concrete evidence (a named passing test, a ledger row, or
a FOUNDER-CHECKLIST entry).

## The five states

| State | Meaning |
|---|---|
| `built-tested` | Implemented and covered by automated tests (cargo/vitest) that pass on the coordinator machine. Not necessarily exercised against real models, real hardware, or real data. |
| `built-verified-live` | `built-tested` PLUS exercised on the founder's machine against real data/models, with the run recorded (BUILD-LOOP ledger or FOUNDER-CHECKLIST). |
| `built-mock-only` | The code path is complete and tested, but only deterministic mocks have ever driven it — no real model has produced output through it, and/or nothing in the shipped app schedules it. |
| `partial` | A named part of the obligation works; a named remainder does not. The evidence column says which is which. |
| `not-built` | Nothing beyond (at most) a name, seam, or schema exists. |

Paths are repo-relative. `acceptance.rs::name` means a named test that passes
today. Known reds (currently one: `s02_2` APFS case-only rename on macOS) are
called out where they bite.
