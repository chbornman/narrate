Search - visual retrieval (MS-COCO)

The standard image-text retrieval benchmark: real photos, five human-written captions each. Each caption is a query; the right answer is the photo it describes. This honestly tests the CLIP visual + semantic retrieval the app does - exactly what a self-authored note cannot, since a planted note only tests search finding its own injected text.

For 5002 real caption queries against 1000 photos, CLIP visual search puts the correct photo in the top 10 about 95.7% of the time. This is the full COCO-1K benchmark - a genuine, vetted measurement at scale, a world apart from the 7-query journal sketch.

Why lower than a smaller run: a 100-photo / 500-query slice scored higher (nDCG 0.954, Recall@10 0.996) simply because there are fewer distractor photos to rank against. The 1000-photo number is the more honest one: 10x more photos competing for each query's top-10, and CLIP still lands the right one 95.7% of the time. (All sweep configs scored identically - with only the visual signal present, the fusion knobs do not move a single-signal ranking, as expected.)
Honest scope: COCO photos carry no notes, so this measures PURE VISUAL retrieval (the CLIP S4 signal). The fusion knobs (how much to weight your written notes vs. the visual match) do not move a single-signal ranking, so they cannot be tuned here. Tuning that balance needs a library with REAL notes - and the current dogfood library's notes are test junk, so that benchmark is not yet meaningful. Visual retrieval is benchmarkable today; notes-fusion tuning waits on a real reviewed library.

FP16 / CoreML retrieval parity (June 14 2026)

This same COCO-1k harness was the gate for switching the CLIP embedder from int8/CPU to FP16 on CoreML (Apple Neural Engine / GPU), which runs 8.77x faster (18 to 162 img/min). The question: does the faster path retrieve as well? The 1000 images were re-embedded under FP16/CoreML and the 5002 caption queries re-run:

signalint8 / CPUFP16 / CoreMLdelta
nDCG@100.82250.8212-0.16%
Recall@100.95680.9572+0.04%
MRR0.78170.7797-0.26%

Statistically identical - the deltas are pure noise (Recall@10 even ticked up). FP16 is near-lossless (cosine vs the fp32 source 0.99998; CoreML vs CPU 0.9987), so the 8.77x speedup costs nothing in retrieval quality. This cleared the gate to flip the default to FP16/CoreML on the M1 Pro. See SPIKE-COREML.md.

Voice - transcription (LibriSpeech)

The standard ASR benchmark, built from public-domain audiobooks: 40+ readers, clean per-utterance reference transcripts, a dev split to tune on and a test split to report on. Utterances are joined with a 0.5s silence gap so the endpointer has real boundaries to find. The metric is gating-cost = gated WER minus raw WER, isolating pipeline truncation from the model's own error.

Result (LibriSpeech dev-clean, 3-chapter sweep subset)

0.000
gating-cost
gated WER minus raw WER
10.5%
WER (default)
Nemotron 0.6B int8

Two findings. First, gating-cost is 0.0 - the gated (production) transcript matches the raw (gate-forced-open) transcript exactly, so the VAD + endpointer truncate nothing on this clean, gap-segmented audio; the pipeline costs nothing over the model's own error. Second, the sweep shows the snappiness dial matters: dropping rule2 from the default 1.2s to 1.0s worsens WER (10.5% -> 11.8%), so the more aggressive endpoint is not free - the default is the better setting on this corpus. The ~10.5% WER is the streaming 0.6B int8 model's own accuracy on LibriSpeech dev-clean.

Scope: this is the fast 3-chapter sweep subset (30 utterances) for dial iteration; a full-split run + the test-clean confirmation are one command each (scripts/fetch-voice-corpus.sh already staged both splits). Gating-cost is 0 because LibriSpeech is clean, well-segmented read speech with inserted inter-utterance silence - real messy dictation may show non-zero truncation, which is exactly what this metric is built to catch.

How these are produced

All reusable, committed scripts + binaries (the corpora themselves are gitignored - they hold real data and stay local):

  # search: stage a real photo+caption benchmark, ingest into a throwaway eval
  # library, CLIP-embed, build the golden set, sweep
  scripts/fetch-image-benchmark.sh 1000
  pp-eval-ingest --images .../coco5k/images --lib /tmp/coco-eval-lib \
    --captions .../captions.json --out-golden .../coco-golden.json
  pp-sweep search --db /tmp/coco-eval-lib/photoproof.db \
    --queries .../coco-golden.json --models-dir <models> --json

  # voice: stage a real audiobook benchmark, sweep the endpoint dials
  scripts/fetch-voice-corpus.sh dev-clean
  pp-sweep voice --corpus-manifest .../dev-clean-sweep-subset.tsv \
    --grid "rule2=0.8,1.0,1.2" --model-dir <asr> --server <pp-asr-server> --json

The loop these feed

pp-sweep PROPOSES a better config (you commit it - the machine never auto-changes a setting). make tune-check guards against regressions: it re-runs the cheap synthetic benches and fails if a deterministic quality metric drops (perf is warn-only, since it is machine-variable). Contracts (the <100ms search budget, the timing invariants) stay fixed; only the dials are tuned. See DESIGN-TUNING-LOOP.md.

Photoproof benchmarks - real public data, run on the founder machine. Numbers are measured, not modeled. The saved JSON in docs/benchmarks/ is the reviewable record.
